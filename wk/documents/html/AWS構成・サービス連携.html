3. 各サービスの詳細

■ Amazon Cognito（User Pool + Google連携）

ログイン機能そのもの。「Googleアカウントでログイン」ボタンを押すとCognitoのHosted UIに飛び、 Cognitoが裏でGoogleと認可コードのやり取りをして、最終的にアプリ向けのIDトークン（JWT）を発行する。 このJWTがAPI Gatewayでの認証に使われる。
なぜCognito: 自前でパスワード管理・OAuthフローを実装する必要が無く、 Googleログインの実装をCognitoに任せられる。API GatewayのCognitoAuthorizerと 標準で統合できる点も採用理由。

■ Amazon API Gateway（REST API）

フロントエンドが呼び出す全エンドポイント（/recommendations、/chat、 /posts等）の窓口。ログイン必須のエンドポイントにはCognitoAuthorizerを アタッチしており、JWTが無効・未提示なら該当Lambdaを呼ばずに401を返す。
なぜAPI Gateway: Lambdaを直接インターネットに公開せず、認証・CORS・ ルーティングを一括管理できる。統合タイムアウトが29秒固定という制約があり、これが AIチャット（同期呼び出し、Lambda側25秒に短縮）とAI分析（非同期呼び出しに変更）の 設計判断に直接影響している（詳細設計.html参照）。

■ AWS Lambda（API系・バッチ系の2パッケージ）

実処理の本体。backend/lambda/api/（17関数、handlers.py）と backend/lambda/batch/（5関数、generate_score.py等）の2つのSAM CodeUriパッケージに分かれており、この2つの間でコードは共有できない （batch_common.pyのようなヘルパーが両パッケージに重複して存在する理由）。
なぜLambda（サーバーレス）: 個人利用規模のトラフィックでは 「常時起動のサーバー」は過剰投資になる。呼ばれた時だけ課金される従量課金と、 インフラ管理不要な点を重視した。
なぜAPI系とバッチ系を分けたか: API系はユーザー操作に対して 即座に応答する軽量な処理（DynamoDBの読み書き中心）、バッチ系はGoogle Places APIや Claude APIを呼ぶ時間のかかる処理、という性質の違いがあるため。バッチ系は adminRunAiBatchのように「本体を非同期起動するだけの薄いLambda」を挟む 構成にして、API Gatewayの29秒タイムアウトを回避している。

■ Amazon DynamoDB（7テーブル）

テーブル名役割
fishing-spots釣り場マスタ（座標・名前・魚種・写真URL等）
fishing-recommendationsスポットごとの最新スコア・AIコメント（1スポット1件、上書き型）
fishing-favoritesお気に入り登録
fishing-posts釣果投稿（本文・写真・釣れた魚種）
fishing-chatsAI相談チャットの会話履歴
fishing-usage1日あたりのAI/API呼び出し回数（レート制限用、TTLで自動削除）
fishing-usersユーザーの表示名（ユーザー名）
なぜDynamoDB: スキーマがシンプルでアクセスパターンも 単純（PK検索・全件scan中心）なため、RDBのような複雑なクエリは不要。 PAY_PER_REQUESTモードで使った分だけ課金され、サーバーレスLambdaとの相性も良い。

■ Amazon S3（2バケット）

①フロントエンド配信用バケット：Reactのビルド成果物（HTML/JS/CSS）を置き、 CloudFrontがここを参照する。②UploadsBucket：ユーザーが投稿・ スポットに設定する写真の保存先。フロントはLambda（presignUploadHandler） から発行される署名付きPOSTフォームを使ってブラウザから直接S3へアップロードし、 Lambda自体は画像バイナリを経由しない（API Gatewayのペイロードサイズ制限回避のため）。
なぜ署名付きアップロード: 画像バイナリをLambda経由にすると API Gatewayのペイロード上限に引っかかる。S3への直接アップロードにすることで この制約を回避しつつ、content-length-range条件でアップロード上限 （8MB）をS3側に強制させている。

■ Amazon CloudFront ＋ Cloudflare Workers（フロント配信が2系統ある理由）

本番の正系はCloudFront（S3をオリジンとするCDN）。index.htmlは no-cache、ハッシュ付きアセット（/assets/index-<hash>.js）は 長期キャッシュという構成。加えて、独自ドメインを取得する前の段階で見た目の良い URLを用意するため、Cloudflare Workers（*.workers.devの無料サブドメイン）に も同じビルド成果物を並行デプロイしている。バックエンドAPI（API Gateway）はAWS側 1本のみで共有しており、フロントの配信経路だけが2系統ある形。

■ AWS Systems Manager Parameter Store（SSM）

Claude APIキー（/fishing-ai/anthropic-api-key）とGoogle Places APIキー （/fishing-ai/google-places-api-key）をSecureStringとして保管。 Lambdaの環境変数に直書きせず、実行時にssm:GetParameterで取得する。
なぜSSM: 環境変数への直書きよりも安全（IAMで読み取り権限を 個別Lambdaごとに絞れる、CloudFormationのコード上に平文キーが残らない）。 AWS Secrets Managerより低コストな点も理由（Standard利用なら無料）。

■ Amazon EventBridge

cron(0 21 * * ? *)（UTC 21:00 = 日本時間AM6:00）で generateSpotScoreBatchを毎日自動起動し、全スポットのスコアを 最新化する。ユーザーが「AI分析を実行」ボタンを押さなくても、朝には最新の おすすめが用意されている状態を作るための仕組み。

■ AWS Budgets

月$10のAWS利用料予算を設定し、80%/100%到達時にメールで通知する （template.yamlのCostBudgetリソース）。 ただしこれはAWS側の課金のみを見ており、Google Cloud（Places/Maps）や Anthropic（Claude）の課金はAWSの外で発生するため対象外。それぞれ Google Cloud ConsoleとAnthropic Console側で別途予算アラート・spend limitの 設定が必要（README.md「10. 利用料アラート」参照）。

■ AWS IAM（最小権限方針）

各Lambda関数には、その関数が実際に必要とするDynamoDBテーブル・S3バケット・ SSMパラメータへのアクセス権限だけをSAMのPolicies（ DynamoDBCrudPolicy・S3WritePolicy・ SSMParameterReadPolicy等）で個別に付与している。 例えばgetSpotsHandlerはSpotsテーブルの読み取りしかできず、 書き込みや他テーブルへのアクセス権限は持たない。

4. 主要フローのサービス連携トレース

① ログイン

ブラウザ「ログイン」クリック
 → Cognito Hosted UI
 → Google認証画面（Cognitoが仲介）
 → Cognitoに戻りIDトークン（JWT）発行
 → フロントがJWTを保持し、以後のAPIリクエストにAuthorizationヘッダーとして付与

② 「AI分析を実行」ボタン

フロント → API Gateway → adminRunAiBatch（Lambda、UsageTableでレート制限チェック）
 → generateSpotScoreBatch を非同期起動して即202を返す
 → generateSpotScoreBatch が裏側で実行:
    SpotsTable全件取得
     → discover_spots.run_discovery()で新規スポット探索（Google Places API、SSMからキー取得）
     → 各スポットの天気・潮汐取得（Open-Meteo、APIキー不要）
     → スコア計算（ルールベース）
     → スコアが大きく動いたスポットのみClaude APIで理由文生成（SSMからキー取得）
     → RecommendationsTableへ保存
 → フロントは GET /recommendations を数秒おきにポーリングして完了を検知

③ AI相談チャット（画像添付あり）

フロント → API Gateway（CognitoAuthorizerでJWT検証）→ postChatHandler
 → UsageTableでレート制限チェック（1日30件）
 → S3(Uploads)から画像バイトを取得
 → SpotsTable・RecommendationsTableをscanして実データのコンテキストを構築
 → Claude APIへテキスト＋画像＋実データコンテキストを送信（SSMからキー取得）
 → 応答をChatsTableに保存し、同期的にフロントへ返却

④ 写真アップロード（釣果投稿・スポット写真）

フロント → presignUploadHandler（Lambda）が署名付きPOSTフォームを発行
 → ブラウザがS3(Uploads)へ直接POST（Lambda/API Gatewayを経由しない）
 → アップロード完了後、公開URLをPosts/SpotsテーブルにLambda経由で保存

5. なぜこの構成にしたか（設計方針まとめ）

  • サーバーレス徹底: 個人利用規模のトラフィックに対して常時稼働のサーバーは過剰。 使った分だけ課金されるLambda・DynamoDB・S3（+CloudFront）で構成し、待機コストをゼロに近づけている
  • バッチ中心・リアルタイム処理の排除: スコア計算はEventBridgeの日次バッチと手動実行の 2経路に絞り、常時ポーリングするような設計を避けている
  • 実データとAI生成の分離: 座標・実在性など「間違えられないデータ」はGoogle Places API のみを情報源とし、AI（Claude）は説明文生成や魚種推測など「間違っても実害が小さい付随情報」 にのみ使う（ハルシネーション対策）
  • 最小権限のIAM: Lambdaごとに必要なリソースへのアクセス権限だけを絞って付与
  • コスト保護の多層化: ①ユーザー単位の1日あたりレート制限（UsageTable）、 ②AWS Budgets（AWS利用料）、③Google Cloud・Anthropic Console側の予算アラート（AWS外の課金）、 という3層でコスト暴走を防ぐ設計にしている
