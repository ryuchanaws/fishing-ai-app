Lambda詳細設計書（実務版）

本設計書は、釣行AIアプリにおけるAWS Lambda関数単位の責務・入出力・処理フローを定義する。

1. 設計方針

  • 1 Lambda = 1責務（単一責任原則）
  • API系とバッチ系を分離
  • DynamoDBアクセスは原則Lambda経由
  • リアルタイム処理は禁止（バッチ中心）

【2026-07-24 実装更新・同日中に再変更】ユーザーからのフィードバックにより、「新スポットを探す」を独立ボタンのまま 残すのではなく、generateSpotScoreBatch が discover_spots.run_discovery() を内部で呼び出す形に統合した。 「AI分析を実行」ボタンを押すたびに (a) 位置指定なしの全国向け探索 → (b) 全スポットのスコア計算、の順に実行される。 これに伴い discoverSpotsBatch の週次EventBridgeスケジュールは冗長になったため廃止し、この関数は 「現在地から新スポットを探す」ボタン（ユーザーの現在地に絞った近傍探索専用、半径15km、スコア計算はしない） 専用として存続させている。

実装上は generate_score.py と discover_spots.py の相互import（循環import）を避けるため、 共有ヘルパー（DynamoDB/SSMアクセス等）を新設の batch_common.py に切り出し、両者がそこから import する構成にした。

4. 個別設計

getRecommendationsHandler

目的：ユーザーにTOP3スポットを返却

入力

{
  "userId": "xxx",
  "lat": 35.6,
  "lng": 139.7
}

処理フロー

1. Recommendations取得
2. 距離補正
3. スコア順ソート
4. TOP3抽出
5. レスポンス返却

出力

{
  "top3": [
    {
      "spotId": "A123",
      "score": 87,
      "fishTypes": ["アジ"],
      "reason": "潮流が安定",
      "distance": 3.2,
      "cost": 500
    }
  ]
}
---

generateSpotScoreBatch

目的：AIによる釣行スコア生成

処理

Spots取得
 + Weatherデータ（Open-Meteo Forecast API）
 + Tideデータ（Open-Meteo Marine API・海面水位）
 → スコア計算
 → Gemini APIで推薦理由(reason)を生成
 → DynamoDB更新

天気・潮汐データソース【2026-07-23 実装】

外部の天気・潮汐APIは Open-Meteo（https://open-meteo.com/）を採用。 APIキー登録不要・無料（非商用）で、複数の気象・海洋機関のデータを統合しており信頼性が高い。
・天気スコア：weather_code（WMO天気コード）・降水量・風速から独自ヒューリスティックで算出
・潮汐スコア：sea_level_height_msl（海面水位）の前後1時間の変化率から算出 　（潮が動いている時間帯ほど魚の活性が上がるという経験則に基づく）
・外部API呼び出しが失敗した場合はシミュレーション値にフォールバックし、バッチ全体は継続する

スコアロジック

score =
  fish_probability * 0.4
+ weather_score * 0.2
+ tide_score * 0.2
- distance_penalty * 0.1
- cost_penalty * 0.1

adminRunAiBatch【2026-07-23 追記】

目的：フロントの「AI分析を実行」ボタンから generateSpotScoreBatch を起動する
API Gateway（REST API）は統合タイムアウトが29秒固定であり、Gemini API呼び出しを含む generateSpotScoreBatch（5スポット分）はこれを超えることがある。当初は同期呼び出し （RequestResponse）で実装していたため、Lambda自体は成功しているのに API Gateway が 504 timeoutを返し、ボタンにエラー表示が出る問題があった。

対応として adminRunAiBatch は generateSpotScoreBatch を非同期呼び出し（Event）に変更し、 起動受付（202）を即座に返す方式に変更した。完了確認はフロントエンド側で GET /recommendations を定期的にポーリングして行う。

discover_spots.run_discovery()【2026-07-24 追加】

目的：新規釣りスポット候補をGoogle Places APIで探索し、Spotsテーブルに追加する中核ロジック。 generateSpotScoreBatch のhandler冒頭（位置指定なし）と、discoverSpotsBatch のhandler （「現在地から新スポットを探す」ボタン経由、位置指定あり）の両方から呼ばれる共通関数。

処理

Spots全件取得（重複判定用）
 → Google Places API Text Search
    ・位置指定なし: "釣り 堤防" 等の全国向け複数クエリ
    ・位置指定あり: "釣り" 1クエリ + location/radius(15km)パラメータで近傍に絞り込み
 → 既存スポットと緯度経度がhaversine距離300m以内なら重複として除外
 → Gemini APIで地名・住所から想定される魚種を推測（失敗時は汎用デフォルト）
 → 基準地点（位置指定時はその座標、なければ東京駅）からのdistanceKmを算出
 → Spotsテーブルへput_item
座標・スポット名などの実在性に関わる情報はGoogle Places APIの結果のみを採用し、 LLM（Gemini）には生成させない（存在しない場所をAIが作り出すハルシネーションを避けるため）。 Geminiは魚種の推測という、実在性に影響しない付随情報の生成にのみ用いる。
generate_score.py が discover_spots.py の run_discovery() を直接importして呼び出すため、 逆方向のimport（discover_spots→generate_score）は循環importになり不可能。共有ヘルパー （DynamoDB/SSMアクセス・HTTP GET）は batch_common.py に切り出し、両モジュールがそこから import する。

presignUploadHandler / updateSpotImageHandler / createPostHandler【2026-07-24 追加】

目的：スポット写真・投稿写真のアップロードと、釣果投稿の作成

処理フロー（写真アップロード）【2026-07-25 方式変更】

1. フロントが POST /uploads/presign を呼び、S3への署名付きPOSTフォーム（uploadUrl + uploadFields、有効期限5分）を取得
2. フロントがそのフォームへ画像ファイルをmultipart/form-dataでPOST（Lambda/API Gatewayを経由しない。ペイロード制限回避のため）
3. アップロード完了後、公開URL（publicUrl）を
   PUT /spots/{spotId}/image （スポット写真）または
   POST /posts のimageUrl（投稿写真）または
   POST /chat のimageUrl（チャット添付）として保存
アップロード先S3バケット（UploadsBucket）はGetObjectのみ公開許可、書き込みは署名付きURL経由のみに限定している。
【2026-07-25】当初は `generate_presigned_url("put_object")` による単純な署名付きPUT URLだったが、 URL自体にサイズ制限を埋め込めずクライアントが任意サイズをアップロードできる欠陥があった。 `generate_presigned_post` に変更し、Conditions に `["content-length-range", 1, 8388608]`（8MB）を指定することで S3側にアップロード上限を強制させている。

postChatHandler / getChatsHandler / getChatHandler【2026-07-25 追加】

目的：写真添付にも対応したAIチャット機能。「カメラ機能」と「チャット機能」を別々に作る案もあったが、 ユーザーの意向により写真添付（端末アルバムから選択 or その場で撮影、どちらも同じ <input type="file">で実現し、撮影用は capture="environment" 属性を付与）をチャット入力の一部として統合した。

処理フロー（POST /chat）

1. chatId が未指定なら新規チャットとしてuuid発行、指定されていればChatsTableから既存messagesを読み込み
2. ユーザーメッセージ（+ imageUrlがあればS3から画像バイトを取得）をmessagesに追記
3. Geminiへ直近10往復分の会話履歴 + 今回のメッセージ（+画像）をマルチモーダル入力として送信
   （システムプロンプトで「釣りの専門家アシスタント」という役割を明示）
4. 応答をmessagesに追記し、ChatsTableへput_item（アイテム全体を上書き）
5. { chatId, reply, updatedAt } を同期的に返却
他のAI機能（generateSpotScoreBatch等）は API Gateway の29秒タイムアウトを避けるため 非同期トリガー+ポーリング方式を採っているが、チャットはUX上ポーリングが合わないため 同期呼び出しのままとし、Lambda Timeoutを29秒より短い25秒に設定することで対処した （テキスト+画像1枚のGemini呼び出しは通常数秒〜十数秒で収まる想定）。
GET /chats は履歴パネルの一覧表示用に messages を含まない軽量なレスポンス（chatId/title/updatedAtのみ）を返す。 GET /chats/{chatId} は履歴から会話を再開する際に全メッセージを返す。「新しい会話」開始時はDBに何も書き込まず、 次にメッセージを送信した時点で初めて新規チャットとして保存される。
【2026-07-26追加】友人にアプリを共有し複数人が使うようになったことで、Gemini API呼び出し（＝課金）が 想定外に増えるリスクが生じた。認証実装により実ユーザーIDが取得できるようになったことを利用し、 postChatHandlerの冒頭でGemini呼び出し前に _check_and_increment_daily_usage(user_id, "chat", DAILY_CHAT_LIMIT) を呼ぶようにした。UsageTable（userId + dateKey複合キー、dateKeyは"chat#2026-07-26"の形式）への update_item（ADD式によるアトミック加算）で当日のカウントを取得・加算し、 1日30件（DAILY_CHAT_LIMIT）を超えていれば429（{"error": "rate_limited", ...}）を返して Geminiを呼ばずに終了する。UsageTableの各アイテムにはTTL（翌々日ごろ）を設定しており、 DynamoDB側で自動的に古いカウンタが削除されるため、明示的なクリーンアップ処理は不要。

6. セキュリティ

  • IAM最小権限
  • Cognito認証必須（操作系エンドポイントのみ）
  • API Gateway認証制御
【2026-07-24 時点・経緯】Cognito認証は当初未実装で、個人利用中心を想定し userId は "user-001" 固定で 運用していた。他の機能（現在地からのおすすめ・画像機能・投稿・新規スポット自動発見）を先に実装したうえで 最後に対応する方針としていた。
【2026-07-26 実装】友人にアプリを共有した結果、固定userIdの限界（全員のお気に入り・AI相談履歴が混ざる、 投稿削除に所有者チェックが無い）が実害になったため、Cognito User Pool + Google IdP（Hosted UI）による Google認証を実装した。要件定義.htmlに明記の「セキュリティ：Google認証（Cognito）」に対応する。

6.1 認証範囲

閲覧は未ログインでも可能（おすすめ・地図・スポット一覧・投稿一覧）。 操作（お気に入り・投稿作成/削除・AI相談・AI分析実行・新スポット探索）はログイン必須という方針とした （誰でも見られるアプリという性質を保ちつつ、書き込み系だけを保護する狙い）。

6.2 認証フロー

フロント（react-oidc-context, Authorization Code + PKCE）
 → Cognito Hosted UI（/oauth2/authorize）へリダイレクト
 → Hosted UI上でGoogleログイン（Cognito側のGoogle IdP連携経由）
 → Cognitoの/oauth2/idpresponseへコールバック → 認可コードをid_tokenに交換
 → 以後のAPIリクエストに Authorization: Bearer <id_token> を付与
 → API Gateway の CognitoAuthorizer（User Pool Authorizer）がid_tokenを検証
 → 検証成功時、Lambda側イベントに event.requestContext.authorizer.claims.sub が入る
 → handlers.py の _get_user_id(event) がこれを実ユーザーIDとして使用
CognitoはOIDC標準の end_session_endpoint をディスカバリドキュメントに含めないため、 ログアウトは react-oidc-context の標準 signoutRedirect() ではなく、 Hosted UI独自の /logout エンドポイントへ直接遷移する方式で実装している （frontend/src/auth/authConfig.ts の cognitoSignOut()）。

6.3 所有者チェック

Favorites/Chatsテーブルは userId がpartition keyの一部のため、他人のuserIdでは そもそも該当データにアクセスできない設計（追加の所有者チェック不要）。 一方Postsテーブルは postId 単一PKで所有者情報がキーに含まれないため、 deletePostHandlerで削除前に get_item して投稿の userId と リクエスト元の userId を比較し、一致しなければ403を返す明示的なチェックを追加した。

7. テスト戦略【2026-07-25 追加】

  • バックエンド: pytest。純粋関数（calc_score・haversine_km等）の単体テストに加え、 moto でDynamoDBをモックしたハンドラーレベルのテスト（投稿・チャットの作成→削除ライフサイクル等）
  • フロントエンド ユニットテスト: Vitest + React Testing Library（utils/の純粋関数、 RecommendationCardのレンダリングテスト）
  • フロントエンド E2E・VRT: Playwright。実AWSには接続せず page.route() でAPIレスポンスを モックする。VRT（toHaveScreenshot）のベースライン画像はCI環境で生成する必要がある （OS依存のため。詳細はREADME参照）
  • CI: .github/workflows/test.yml が pull_request → main をトリガーに実行される （deploy.yml の push → main トリガーとは分離。デプロイは行わずテストのみ）
AIによる自動コードレビュー（Claude API等）はPRごとの課金が発生するため今回は見送った。 GitHub標準のPRレビュー機能（コメント・Approve/Request changes）は追加設定なしで利用できる。

8. まとめ

Lambdaは「API処理」と「バッチ処理」に完全分離し、 スケーラブルかつ低コストな構成とする。
